# Izanami Lab 自动优化器 —— 核心算法分析报告

> 分析对象：补丁作者的完整模拟器 `Izanami-Lab-MacOS-integration-full-enhancements-v1112`
> 目的：为「只保留核心算法、完全重写 GUI」提供依据。
> 方法：直接阅读源码（`src/optimizer/*`、`src/learning/*`、`gui/**` 接缝）+ 与官方 v1.1.1.2 基准对比。

## 0. 结论速览

**这个补丁的算法层与 GUI 层在代码上是干净分离的。**

| 层 | 代码量 | 处置建议 |
| --- | --- | --- |
| 核心算法 `src/optimizer/` | **4,022 行 / 22 文件** | 保留，直接复用 |
| AI 学习 `src/learning/` | **1,717 行 / 9 文件** | 可选保留（实验功能，与搜索解耦） |
| GUI 层 `gui/**`（优化器相关） | **3,634 行 / 17 文件** | **完全重写** |
| 测试：算法级 | **33 文件 / 5,319 行** | 保留，作重写的安全网 |
| 测试：GUI 级（`*_ui`/`*_gui`） | **17 文件 / 2,218 行** | 随 GUI 一起重写或丢弃 |

三个决定性事实：

1. **`src/optimizer/` 完全不 import `gui.*`。** 唯一例外是 `update_compat.py`（旧版更新兼容补丁），它不是搜索路径的一部分，可整体删除。
2. **算法与 GUI 的全部耦合只有 7 个键的请求字典 + 一个消息队列。** 换个 GUI 只需构造同样的 `request` 并监听 `queue`。
3. **算法不依赖任何官方文件的改动。** 它把官方 `src/combat_v2/`、`src/data/`、`src/utils/batch_simulator.py` 当作只读引擎调用——而 `batch_simulator.py` **不在补丁修改的 22 个文件清单里**，说明作者没有为了优化器去改官方引擎。

## 1. 算法在做什么

**一句话**：把官方「战术演习」五回合战斗当成一个黑箱评分函数，用多阶段分层搜索，在**站位 × 共享回忆**的离散空间里找期望得分最高的配装。

**唯一的评分来源**（`engine.py:103-114`）：

```python
controller = TacticalExerciseController(bf, BattleConfig(max_turns=5, enable_rdps=False), ...)
result = controller.execute_battle()
return float(result["score"]["total_score"])
```

评分语义 = **对敌伤害 − 敌方回复**，是官方 `total_score`，**没有自建伤害或评分公式**。

**搜索维度**（受模式限制）：

| 维度 | 状态 | 说明 |
| --- | --- | --- |
| 站位（6 格） | ✅ 可用 | 720 / 360 / 120 种合法排列 |
| 共享回忆（6 张） | ✅ 可用 | 无序集合，`C(池, 6-必选)` |
| 角色阵容（换人） | ⚠️ 代码在、UI 冻结 | `change_fifth` 恒为 False |
| 模块词条 | ⚠️ 代码在、UI 冻结 | `change_affixes` 恒为 False |

**空间数学**（已核对源码）：

- **站位**（`position_search.py:47-56`）：对 `5 名角色 + 1 个 None` 做全排列 = **6! = 720**，再用硬约束逐角色过滤。原阵容若合法则**排到首位**（保证基线先评价）。约束类型：`any` / `front`（槽 1-3）/ `back`（槽 4-6）/ `fixed`（指定槽）/ `keep`（锁在原槽）。
- **回忆**（`memory_search.py:13-24`）：`总组合数 = C(候选池大小, 6 - 必选数)`；**按集合（无序）**，因为共享回忆效果与槽位无关。评价前统一 `sorted(memory_ids)`。
- **联合空间**：`入围站位数 × 回忆组合数`（每套站位各有一份过滤后的回忆空间，剪枝开启时逐站位计算）。
- 若 `change_fifth` 或 `change_affixes` 为真，理论联合空间**故意留空**（`budget.py:31-32` 的 `theoretical = None`）——因为换人与词条是"修复/邻域"语义，可达基数不可安全计算。

> **重要**：`SearchSettings` 里 `change_fifth` / `change_affixes` 的**算法实现是完整的**（`mutate()`、`prepare_search_snapshot()` 都支持），只是 GUI 强制关闭并标注「开发未完成」。重写 GUI 时这是**可以重新开放的产品决策**，不需要动算法。

## 3. 完整算法流水线（layered 模式）

```
run_layered_search(search)                      layered_search.py:449
  └─ LayeredRun.run()                           layered_search.py:370
       ├─ [预算门禁] budget < 站位总数 × 2 → 拒绝    :377-381
       ├─ preselect()                            :207
       │    ├─ 若 quick+filter → bare_preselection.run()
       │    └─ 否则 V2.8 旧路径（elite_reference + paired_gate）
       │         · 基础 2 种子，冻结前 ceil(P×10%) 精英
       │         · 追加第 3..max 种子（elite_gate 保守保留）
       ├─ _plan_joint()                          :276
       │    ├─ joint_total = 入围站位数 × 回忆组合数
       │    └─ 若开启 → memory_validity 逐站位剪枝，重算 actual_joint_total
       ├─ cover()                                :333
       │    └─ crossed_indices() 平衡拉丁扫掠，站位×回忆完整覆盖
       ├─ [入围]                                  :388-410
       │    ├─ quick → joint_admission.select()（前K+同分+站位代表）
       │    └─ rigorous → 按比例取前 count 名
       │    └─ 人工基线若合法则额外保留为对照
       ├─ review_dispatch.review(...)             :419
       │    └─ quick → quick_review.review()  |  rigorous → statistical_review.review()
       │         └─ 内部调用 final_review.run_finals()（50 + 必要时 100）
       │              └─ finally: combined_score.combine(search)
       └─ finish(reason, detail)                  :431
```

### 3.1 精确阈值与常量

**裸装预选**（`bare_preselection.py`）：

| 常量 | 值 | 位置 | 语义 |
| --- | --- | --- | --- |
| 基础种子 | **2** | `SearchSettings.layered_base_seeds` | 全部站位统一评 2 种子 |
| 最大种子 | **4** | `layered_max_seeds` | quick 路径实际补到 **8** |
| 精英比例 | **10%** | `elite_reference` `math.ceil(len(rows)*.1)` | 冻结参考组 |
| 4 种子线 | **97%** | `four_qualification(drop_percent=3)` | `C4 ≥ R4×0.97` |
| 8 种子线 | **97%** | `eight_qualification(drop_percent=3)` | `C8 ≥ R8×0.97` |
| 最终参考 | 前 **12** 名均值的 **95%** | `competitive_selection(top_count=12, drop_percent=5)` | |
| 晋级名次 | **60** | `rank_limit=60` | 第 60 名同分全保留 |
| 同分容差 | **8 ULP，最低 1e-12** | `same_score()` | **不用显示分数** |

**快速复评**（`quick_review.py:6-9`）：

```python
LOOKS = (8, 16, 32, 64, 128, 256)     # 累计共同种子数
CAPS  = (64, 32, 16,  8,   4,   4)     # 竞争者名额上限
GAPS  = (.05,.03,.02,.01,.005,.005)    # 允许落后比例
NOISE_MULTIPLIER = 3.
```

淘汰判定（`empirical_gap`，:33-42）：

```python
valid = n >= 8 and se 有效 and reference > 0
cut   = mean > max(ratio*reference, 3*se)     # 同时超过阈值和 3×SE 才淘汰
```

名额分配（`retain`，:45-57）：**75% 给均分领先者，25% 给 `mean - 3SE` 最小的"可能挑战者"**；领先者与人工基线**永不淘汰**。

**决赛**（`final_review.py`）：

| 项 | 值 | 位置 |
| --- | --- | --- |
| 初评种子 | **50** | `budget.INITIAL_SEEDS` |
| 加赛种子 | **100** | `budget.EXTRA_SEEDS` |
| Bonferroni | `alpha = .05 / (pairs × 2)` | :19，**在见到任一阶段前就固定** |
| 种子起点 | `seed + 1000000000` | :21，避开所有已用种子 |

**综合冠军**（`combined_score.py:30`）：

```python
seeds = sorted(common_review | common_final)   # 取并集，不是相加
combined_mean = mean(cache[k, s] for s in seeds)
```

文档 `OPTIMIZER_V28.md:40` 给出确切语义：

> 用每个成员最后完整复评种子的交集及该决赛阶段完整种子的交集，从真实缓存计算去重并集均分。
> **128＋50=178，128＋150=278，256＋150=406，512＋150=662**。
> 嵌套历史轮次不重复相加；**50 和 150 不相加成 200**；50-only 候选保留历史组但不加入 150 组。

即：150 是"50 初评 + 100 加赛"的累计观察点，取**并集**得到 150 而非 200；复评侧 128/256/512 来自**严谨模式**的 `validation_seeds` 倍增（`statistical_review.py:87-90`，从 `min(4, validation_seeds)` 起每轮 ×2），而快速模式上限是 256（`quick_review.LOOKS`）。

### 3.2 关键设计不变量

- **预算账本**：`_budget_spent()` 取 `max(done, submitted_tasks)` —— **失败/未知任务也占预算**，不会被当成"未花掉"。
- **缓存键**：`configuration_key(state)` = 规范化 `active_snapshot` 的 SHA256，**回忆排序后**（无序集合语义），未上场角色的参数被剔除。
- **共同种子**：所有比较只用同一组种子；`paired_gate` 在共同样本 < 2 时**保守保留**。
- **停止语义**：只在种子边界检查；未完成的共同种子组**不发布均分**。
- **无 GUI 依赖**：`parallel.py:3` 明确注释 *"No GUI imports"*。

## 4. 算法 ↔ GUI 的接口（重写依据）

### 4.1 启动一次搜索（GUI → 算法）

唯一的契约是 **7 个键的 `request` 字典**（`auto_optimize.py:546-548`）：

```python
request = {
    "base_path":     str(_BASE_PATH),          # 官方仓库根
    "user_data_dir": str(...),                 # 用户数据目录
    "state":         input_state,              # snapshot 字典
    "constraints":   constraints,              # 约束字典
    "settings":      asdict(SearchSettings),   # 全部参数
    "output":        ".../search-<ts>.json",   # 结果落盘路径
    "learning_path": ".../evaluations.sqlite3" # 可选，AI 学习
}
```

启动方式（`auto_optimize.py:560-563`）：

```python
context = mp.get_context("spawn")
queue, stop_event = context.Queue(), context.Event()
process = context.Process(target=search_worker,
                          args=(copy.deepcopy(request), stop_event, queue),
                          daemon=False)
process.start()
```

**新 GUI 只需要做这 6 行。** `stop_event.set()` 停止；轮询 `queue` 收消息。

**算法侧对宿主只有 4 个纯 callable 依赖**（全部由 `worker.py` 内部构造，新 GUI 无需直接提供）：

| 契约 | 构造位置 | 形态 | 语义 |
| --- | --- | --- | --- |
| `stop` | `BattlePool(stop=stop_event.is_set)`、`BudgetedSearch(stop=stop_event.is_set)` | `() -> bool` | 在种子边界轮询，抛出 `Stopped` |
| `progress` | `BudgetedSearch(progress=lambda result: queue.put(...))` | `(dict) -> None` | 完整结果包 |
| `heartbeat` | `BudgetedSearch(heartbeat=lambda result: queue.put(...))` | `(dict) -> None` | 轻量心跳包 |
| `warning` | `RecordingSession(warning=lambda text: queue.put(...))` | `(str) -> None` | 学习采集告警 |

`progress` 与 `heartbeat` **投的是同一种消息类型 `progress`**，靠 payload 里的 `progress_only` 布尔区分。新 GUI 必须按这个字段分拣，否则会把心跳当成完整结果渲染。

**停止语义细节**：`BattlePool(stop_timeout=3)` —— 收到停止后最多等 **3 秒**让在途战斗收尾；`replay_worker` **没有** stop_event，不可中断。

**消息类型只有 5 种**，从 worker 侧 `put` 的位置可穷举：

| type | 产生位置 | 备注 |
| --- | --- | --- |
| `progress` | `worker.py:52-54`（progress + heartbeat 两处） | 靠 `progress_only` 区分 |
| `learning_warning` | `worker.py:45` + `:49`（采集初始化失败兜底） | |
| `error` | `worker.py:71` | `{message, summary, diagnostic_log}` |
| `replay` | `worker.py:90` | `{path, score, seed}` |
| `exit` | `worker.py:79`（`finally` 无条件） | 进程结束标志 |

**队列背压**：`_destroyed()` 特意起了一个 **10 秒**的后台线程继续排空 queue —— 注释说明否则大 final snapshot 会阻塞协调进程的队列 flush。新 GUI 若不做等价处理，关闭窗口时可能卡住后台进程。

**心跳节流**：`heartbeat()` 默认 `progress_interval = 0.5` 秒一次（`search.py:236-239`，下限 0.1 秒）；完整报告另有 ≥2 秒的最小间隔（`report()` :280-283）。

### 4.3 心跳/完整包的分层（重要设计）

`report_fields(final, heartbeat)`（`layered_search.py:116`）会**按用途裁剪字段**：

- `heartbeat=True` → 只回 `dict(layered=info)`，并 **pop 掉大字段**（`position_records`、`first_eight_configuration_keys`）
- `final=True` → 追加 `joint_candidate_records`、`bare_position_records`、`joint_seed_scores`
- 中间态 → 只回**前 100 套**候选预览

**这条分界线就是"算法字段 vs 展示字段"的现成划分**：心跳包里的字段是给进度条用的，final 包里的才是结果。

`auto_optimize.py:648-654`（进程异常退出时）：
