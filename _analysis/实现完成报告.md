## 一之二、性能：并行化改造（7.24× 提速）

> 用户反馈：「搜索速度太慢了，战斗场数增长非常慢，和我实际模拟战斗相比慢了太多」。
> 实测定位后发现：**单场战斗成本从来不是问题，问题是只跑单进程。**

### 诊断（全部为实测数字）

| 指标 | 实测值 | 结论 |
| --- | ---: | --- |
| 优化器单场战斗 | **277 ms**（3.6 场/秒） | — |
| 官方 batch 单场战斗 | **304 ms**（3.3 场/秒） | **我的反而快 9%** |
| 战场构建耗时 | 0.2 ms | 仅占单场的 **0.1%** |
| 战斗本身 | 249 ms | **99.9%，不可压缩** |
| 单个候选状态 pickle | 2,316 B / 0.02 ms | 占单场 **0.01%**，IPC 可忽略 |
| 每 worker 内存 | **43 MB** | 8 进程约 390 MB，安全 |
| **优化器进程数** | **1** | ← **真正的瓶颈** |
| **官方 batch 进程数** | **16**（`os.cpu_count()`） | ← 参照系 |

根因：`SearchSettings.workers` 此前**被声明、被校验，却从未被读取**——我写了个空壳。

### 修复

新增 `src/optimizer/parallel.py`：spawn 进程池，每个 worker 初始化时各建一个 `Evaluator`（DataLoader 只加载一次/进程）。

**关键细节：派发粒度是「单场战斗」，不是「单候选」。**
第一版按候选派发，把整个种子组交给**一个** worker，结果 24 场只提速 **1.09×**——因为种子数多时等于串行。改成按单场战斗派发后（状态仅 2.3 KB，0.02 ms，占 250 ms 战斗的 0.01%），提速到 **4.6×**。

### 实测结果

| 场景 | 串行 | 并行 | 提速 |
| --- | ---: | ---: | ---: |
| 24 场纯战斗（4 worker） | 7.54s | 2.20s | **3.43×** |
| 24 场纯战斗（8 worker） | 7.54s | 1.64s | **4.60×** |
| 真实搜索 120 场 | 36.09s | 6.86s | **5.26×** |
| **真实搜索 200 场（自动/16 进程）** | **56.0s** | **7.73s** | **7.24×** |

**1200 场预算的投影耗时：339 秒（5.7 分钟） → 47 秒。**

### 正确性（并行必须与串行完全等价）

- **逐位一致**：同一 `(state, seed)` 在池中与串行的分数**完全相同**（93,089,906 / 97,506,767 / 76,470,951）。
- **与进程数无关**：1 worker 与 8 worker 产出**相同冠军、相同候选集、相同排序**。
- 原因是每场战斗显式播种且互不依赖，`imap` 按提交顺序回传结果，故完全可复现。

### 同时修掉的 2 个真实缺陷

1. **`_evaluate_jobs` 解包错误**：`payload` 元素是 `(state, seeds)` 2 元组，我却按 3 元组解包 → **串行路径直接崩溃**。
2. **停止原因的优先级**：用户主动停止与预算不足同时发生时，`"预算不足"` 会压制 `"用户停止"`，报告误导。改为**用户停止优先**。

### GUI

弹窗「高级选项」新增 **战斗进程数**，默认「自动」（= 逻辑核数，与官方 batch 一致）；结果面板新增显示「战斗进程 N 个」。

### 另有一个必须记住的坑

多进程 **spawn** 在 Windows 上会重新导入入口脚本；**调用 `optimizer_worker` 的脚本必须有 `if __name__ == "__main__"` 守卫**，否则子进程会重跑整个脚本并递归 spawn。我自己的 P6 验收脚本起初没加，导致 22 个 python 进程失控累积（已清理）。

生产入口 `gui_app.py` **本来就有**该守卫（L62 `if __name__ == "__main__"` + L64 `multiprocessing.freeze_support()`），所以**生产代码安全**；只有我的临时验收脚本需要补。

## 一之三、回忆卡池 + 预算自动估算（修复「没有候选」）

> 用户反馈：**「预算不足 / 没有候选完成完整的精评种子组」**，并指出回忆卡组合太多无法全局搜索。
> 实测定位到 **3 个真实缺陷**，逐一修复。

### 用户报告的现象

```
【智能优化 · 当日最高 Roll5】
预算 12000 场，实际 15984 场（缓存命中 0），用时 385.7 秒
空间：站位 720 × 回忆 24635248848 = 17737379170560 种
结果：预算不足　预算不足以完成下一个完整 8 种子精评
没有候选完成完整的精评种子组；请提高预算后重试。
```

### 缺陷 1（根因）：预算被超额一倍

`_coarse` 把**战斗预算当作候选数**用，没有除以 `coarse_seeds`。Roll5 需要 2 个粗筛种子，于是：

```
reserve = max(8×2, 12000//3) + 8 = 4008
coarse_cap（当作候选数）= 12000 - 4008 = 7992
实际战斗 = 7992 × 2 = 15984          ← 与用户日志完全一致
refine 门槛：15984 + 8 > 12000 - 8   →  affordable = []  →  零候选
```

**修复**：先把预算换算成候选数（`affordable_battles // coarse_cost`），单位不再漂移。

### 缺陷 2：预算估算不单调 —— 卡池变大反而更便宜

`SCREEN_SAMPLES(600) < COVER_LIMIT(3000)`，所以跨越穷举阈值时采样数**下降**：

| 卡池 | 空间 | 评判 | 预算 |
| --- | ---: | --- | ---: |
| 6 张 | 720 | 穷举 720 | 822 |
| 40 张 | 2,763,633,600 | 采样 **600** | **702** ← 变小了 |

用户看到「卡池变大→预算变小」，会读成「更大的搜索更便宜」。
**修复**：`max(screen_samples, cover_limit)` 兜底 + **单调性测试**（扫过阈值断言预算不降）。

### 缺陷 3：成功的运行被误报为失败

`_refine` 只要 `len(affordable) < len(screened)` 就设 `termination="预算不足"`。
而抽样时**这永远成立**（粗筛覆盖的候选总是多于预算能精评的），
于是排序了 **501 个候选**的正常运行仍显示「预算不足 / 没有候选」。
**修复**：只在**一个候选都排不上**时才报预算不足；否则报「完成」并说明有几个受预算限制未精评。

### 新增：回忆卡池（候选卡池）

弹窗新增 **「必选回忆」** 与 **「候选卡池」** 两个多选器，**搜索只在卡池内进行**。

卡池大小直接决定空间：

| 卡池 | C(n,6) | × 720 站位 |
| ---: | ---: | ---: |
| 6 张 | 1 | 720 |
| 12 张 | 924 | 665,280 |
| 16 张 | 8,008 | 5,765,760 |
| 40 张 | 3,838,380 | 2,763,633,600 |
| **164 张（全卡池）** | **24,635,248,848** | **17,737,379,170,560** |

**默认卡池 = 当前上场的 6 张，且默认不固定任何卡。**
（我最初误设为「6 张全部固定」，测试立刻抓到：`C(pool-6, 0) = 1`，**无论加多少卡组合数都是 1**，卡池将完全失去意义——正是这个功能要消除的困惑。）

### 新增：预算自动估算（`src/optimizer/budget.py`）

不再让用户猜数字。按 **目标 + 卡池 + 强度**（快速/标准/精细）估算：

```
预算 = 粗筛 + 精评 + baseline + 自适应追加
```

并**诚实披露覆盖率**：

```
将抽样评估 3,000 个候选（占空间 0.0000%），其中前 40 名做 8 种子精评；
预计最优候选位于前 0.03%；约需 6,408 场战斗
```

Roll5 因为需要 2 个粗筛种子而更贵（同场景 mean 3,102 vs roll5 6,408）。
低于下限会**拒绝运行并说明原因**，而非白跑一场。

### 修复效果（同一场景：全卡池 164、预算 12000、Roll5）

| | 修复前 | 修复后 |
| --- | --- | --- |
| 战斗数 | 15984（超额） | **12000（守约）** |
| 候选数 | **0** | **501** |
| 结果 | 预算不足 / 没有候选 | **完成** |

### 测试

新增 `tests/test_optimizer_budget.py`（22 项），含**超额回归测试**：
断言旧公式确实产出用户看到的 15984、新公式不超额、且 Roll5 预算下必须能排出候选。

**94 项单元测试 + 8 个验收脚本全部通过。**

### 缩放做法

Tk 画布没有变换能力，所以每张卡先由**既有渲染器**按原尺寸画好（完整走一遍卡框、稀有度徽章、

坐标同步除以倍数。

这样做是为了**复用整条合成链路**，而不是在小尺寸下重写一个渲染器 ——
后者会让缩略图和编队页的卡片长得不一样。

## 二之二、右侧空白修复 + 删除文字版柱形图

> 用户反馈（附截图）：**「搜索结束后 GUI 右侧中央有一大块空白部分」**，
> 并明确**「文字版的候选排行柱形图需要删除」**。

### 空白部分的根因：空 Notebook 仍占了 2/3 高度

`ResultTablePanel` 是**五个标签页共用**的结果面板，内部是垂直 `PanedWindow`：

```python
self._paned.add(self._summary_text, weight=1)   # 报告文本
self._paned.add(self._notebook,     weight=2)   # 表格区
```

优化器只产出文本，于是调 `set_tables([])` —— Notebook 里**一个页签都没有**，
但 `weight=2` 仍然让 PanedWindow 为它保留 **2/3 的高度**，画出来就是一大块空白。

**修复**：新增 `_sync_notebook()`，**无页签时把 Notebook 从窗格中移除**，把权重还给摘要文本；
表格到来时再加回去。

实测对比（同一面板，高 916px）：

| | 修复前 | 修复后 |
| --- | ---: | ---: |
| 摘要文本高度 | 427 | **873** |
| 空 Notebook 高度 | 440 | **1（已移除）** |

**踩到的两个坑**（都由测试抓到）：
1. `panes()` 返回的是**控件路径名字符串**，不是控件对象 —— 用 `in` 直接比控件永远为 False，
   于是「移除」从未生效。改为按 `str()` 比较。
2. 表格到来时 `add()` 报 `already added` —— 需要先判断是否已在窗格中。

### 删除柱形图

柱形图（`█░`）被**移除**：面板宽度下它会把分数挤到第二行，
而十行长度相近的条形**既不澄清顺序**（名次编号已经说清楚了），又徒增竖向噪声。
真正值得表达的层次（哪套阵容赢了）由**下方卡图**承担，不是靠字符长度。

排行改为紧凑两行式，σ 用「万」缩写以适配宽度：

```
═══ 候选排行（前 10 / 共 10）═══

  #1  均值 117,675,272

  #10 均值 109,142,224
       σ442万 CV4.0%　【当前阵容】
（前 3 名的阵容见图）
```

同时清理了随之失效的代码：`_bar`、`BAR_WIDTH/BAR_FULL/BAR_EMPTY`、
以及不再使用的 `format_lineup` / `format_memories` / `SLOT_LABELS` 导入。

## 二之四、勾选标识：把「叉」改成「勾」

> 用户反馈：智能优化弹窗里选中项显示为**「叉」**，直觉上叉不能当作勾选，要求改成**点或勾**。

### 复现与定位

先截图确认，而不是猜。实际渲染出来是：

| 控件 | 选中态 | 问题 |
| --- | --- | --- |
| 搜索维度（**复选框**） | **✗ 叉** | ← 就是这个 |
| 优化目标 / 搜索强度（单选框） | **● 圆点** | 本来就对 |
| 手动指定（未选） | ☐ 空框 | 正常 |

**根因**：Tk 的 `clam` 主题把选中复选框画成「实心方块 + 一个 16px 的字符」，
那个字符在这个尺寸下就是**叉**的形状 —— 与「取消/关闭」无法区分。这是**主题自带的**，不是我们的代码。

### 为什么不直接换主题

对比各主题的选中态：`alt` / `vista` / `winnative` / `xpnative` 画**勾**，
`default` / `classic` 画**实心方块**。

但 `gui/app.py` 对 `clam` 做了大量定制（按钮、输入框、Treeview、Spinbox、滚动条），
换主题会**把这些样式一起丢掉**，只为修一个字符。所以只替换**指示器元素本身**。

### 实现（新增 `gui/widgets/checkmark_indicator.py`）

- Tk **不允许**重定义内置**元素**名（`element_create` 报 `Duplicate element`），
  但**允许**重设内置**布局**名；
- 于是新建一个元素（PIL 绘制，4× 超采样后缩小 —— 直接画 15px 的对角线会毛糙），
  再把内置 `TCheckbutton` 的布局指向它；
- 这样**所有**复选框自动生效，**无需逐个改样式名**，也没有需要同步的样式名；
- 颜色取自当前配色方案，因此**亮/暗两套都正确**（已分别截图确认）；
- 返回 `False` 而非抛异常，`gui/app.py` 侧再包一层 `try` —— 一个装饰性问题不该打断整个样式流程。

### 踩到的坑（都由探针抓出）

| 现象 | 真因 |
| --- | --- |
| `install()` 返回 `True`，但布局没变 | 我把布局写到 `"Tick.TCheckbutton"`，而探针读的是 `"TCheckbutton"` —— **常量写错了**。改为直接覆写内置名 |
| 一度以为「内置名不能改布局」 | 我的对比测试传了**和内置完全相同的布局**，"没变化"什么也证明不了；换成真正不同的布局后才确认**可以改** |
| 以为 `theme_use("clam")` 会重置布局 | 实测**不会**重置；不过样式流程仍会重装一次，所以无论如何都成立 |

### 验证

| --- | --- |
| 内置 `TCheckbutton` 布局指向 tick 元素 | ✅ |

| **单选框未被影响**（仍是 `Radiobutton.indicator`） | ✅ |

## 四、实现中发现并修复的 5 个真实缺陷

两个是**我自己引入的设计错误**，三个是边界条件问题。

### 缺陷 1（严重）：粗筛取前缀 → 只探索邻近排列

按枚举顺序取前 N 个候选，720 空间下 budget=200 只能扫 134 个，**全是字典序靠近当前位置的排列**，空间其余部分永不被看到。

**修复**：`CandidatePlan` 跨空间均匀采样，baseline 恒排首位。并加测试断言"空位必须出现在多个槽位"。

### 缺陷 2（严重，直接影响你的 Roll5 场景）：粗筛按均值排序会淘汰 Roll5 想要的候选

1 个种子时，波动大的候选的成绩**就是一次运气**。实测：

```
empty-slot 5（稳定，spread 2）: 粗筛排名 #1（占据前 8 名全部）
empty-slot 1（波动，spread 120）: 粗筛排名 #120 / 720
```

精评只取粗筛前列 → **波动候选在展现 Roll5 优势前就被淘汰**，而它恰恰是 Roll5 想要的。

**修复**：粗筛改用**目标自身的排序键**；且 Roll5 强制 `coarse_seeds >= 2`（方差需要两个样本）。修复后 Roll5 正确选中波动排列。

### 缺陷 3：baseline 未预留预算

预算紧张时可能全部花在别的候选上，导致**无法判断优化是否真有提升**。改为在粗筛/精评阶段就为其预留一个完整种子组。

### 缺陷 4：`to_dict()` 泄漏原始样本数组

`candidates` 未过滤 `samples` 字段。已修，并加测试断言序列化结果不含 `"samples"`。

### 缺陷 5：空间提示静默吞异常

`except Exception: return None` 掩盖了「候选回忆不足」这类真实错误 —— 用户按开始后才会失败。改为把原因显示在弹窗里。

### 另修一处显示 bug

MEAN 模式下 `format_summary` 把"均值"印两遍（排序键就是均值）。已按目标抑制重复。

3. 弹窗中选择目标（**均值** 或 **当日最高 Roll5**）、搜索范围、预算；如需固定某些回忆，点「选择必选回忆」。
4. **[开始优化]** —— 进度显示在该页结果面板；可随时 **[■ 停止优化]**。
5. 完成后结果面板显示冠军配置、前 30 名排行、与当前阵容的提升幅度。
6. 点 **[✔ 应用最优站位]** 回写站位与回忆到当前页面。

**预算参考**：720 站位场景下，1200 场预算约覆盖 400+ 候选粗筛与 40 个候选的 8 种子精评。Roll5 目标建议 ≥1200；均值目标 600 已够。
