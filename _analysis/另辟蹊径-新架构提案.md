# 另辟蹊径：基于可解析结构的最优配装搜索

> 前提：**放弃作者那套算法**（多阶段共同种子阈值筛选），重新设计。
> 触发这次重新设计的两个事实，来自你的更正 + 我对游戏数据的实测。

---

## 0. 你的更正改变了一切

我原本建议"合并同排等价站位"来压缩 720 种排列。**你指出部分回忆卡是给指定站位位置的角色加成，同排互换会改变收益角色——这个思路确实不成立。**

我随后实测了游戏数据，结果比你的更正更彻底：

| 实测项 | 数值 |
| --- | --- |
| 回忆卡总数 | **164** |
| **引用 `party_position`（指定站位）的卡** | **63 张（38.4%）** |
| `party_position` 的取值 | **1, 2, 4, 5, 7, 8, 16, 18, 32, 48, 56** |
| 解读 | **位掩码**：bit(n−1) = 第 n 号位 |
| 例：`7` = 1+2+4 | 槽 1,2,3 = **整个前排** |
| 例：`56` = 8+16+32 | 槽 4,5,6 = **整个后排** |
| 例：`5` = 1+4 | 槽 1 与 3（跳过 2） |

**所以站位不是"排"的概念，而是精确到 6 个槽位的位掩码。** 同排互换确实会改变收益对象，我的压缩思路作废。

### 而且我发现了自己上一轮"等价站位"结论的**真正原因**

我测出 `back-left ↔ back-right` 在 10 个种子上**分数完全相同**。我当时推断"部分站位排列等价"。**那个推断也是错的。**

真实原因是：**那个测试用的 6 张卡里，没有一张引用后排任意槽位。**

| 测试用卡 | 目标槽位 |
| --- | --- |
| 10001, 10002, 10003, 10004 | 无（全体） |
| 10005 | 仅槽 **1** |
| 10006 | 槽 **1,2,3**（前排） |
| **并集** | **仅 {1,2,3}** |
| **从未被引用的槽位** | **{4,5,6}** |

**所以在那个特定回忆组合下，后排内部怎么换都无所谓。** 这不是"站位等价"，而是"**该回忆组合不看后排**"。

**这个发现把问题的性质彻底改变了**：
> **站位的价值不是内在的，而是由回忆卡的 `party_position` 掩码激活的。**
> 站位搜索和回忆搜索**不是两个可分离的维度**，而是同一个约束满足问题的两面。

**这正是作者算法最根本的缺陷**：它先"用空回忆给站位打分"（`bare_preselection.py:133` 实测 `run.state(row['positions'], [])`），**而这个代理恰好把决定站位价值的机制完全关掉了**。空回忆 = 所有 `party_position` 掩码都不存在 = 站位只有目标选择/行动顺序的微小影响。

## 1. 第二个关键实测：92% 的回忆效果是纯静态的

| 分类 | 数量 | 占比 |
| --- | ---: | ---: |
| **`battle_start` + 纯静态属性修正** | **239** | **91%** |
| `battle_start` 但含动态成分（AcquireMark） | 4 | 2% |
| 非 `battle_start` 触发 | 21 | 8% |

静态效果触及的属性：

```
StatusAttack 92 · StatusMaxHp 37 · StatusDefense 36 · DealtDamage 29
StatusSpeed 27 · StatusCriticalChance 11 · ReceivedHealing 8
CriticalBonusModification 5 · ReceivedDamage 1
```

**而且目标的解析也是纯静态的**（不需要跑战斗）：

```
highlight_targets 143 · ally_position 47 · ally_all 22
ally_front_row 10 · ally_back_row 8 · enemy_front_row 4 ...
```

`highlight_targets` 由卡片的 highlight 选择器解析——即 `party_position` 掩码 / 属性 / 职业 / 类型 / base_master_id，**全部是静态数据**。

### 这意味着一件大事

**"哪张卡给谁加多少属性"可以在零战斗的情况下精确算出来。**

那么"站位 × 回忆"组合的**大部分价值**就有了闭式表达：

```
对每个 (站位排列, 回忆集合)：
    对每张卡、每个 highlight：
        解析出目标角色集合（掩码 ∩ 站位，或属性/职业匹配）
        把静态属性加成累加到这些角色
    得到 5 个角色的最终属性面板
```

这不需要跑一场战斗。**跑战斗只需要用来评估"属性面板 → 实际得分"这一步。**

## 2. 由此得出的新思路

### 2.1 核心洞察

作者算法的根本问题是**把一个可解析的约束满足问题当成了黑箱搜索问题**：

| | 作者的做法 | 问题的真实结构 |
| --- | --- | --- |
| 站位价值来源 | 当作黑箱（跑空回忆战斗） | **由 `party_position` 掩码决定** |
| 站位×回忆关系 | 当作两个可分离维度 | **同一个掩码匹配问题** |
| 回忆效果 | 当作黑箱 | **91% 是静态属性加成** |
| 噪声处理 | 多阶段共同种子筛选 | 应该**先解析、再只对残留不确定性采样** |

### 2.2 建议的新架构（三层）

```
第 1 层：解析层（零战斗）
  ├─ 掩码匹配性剪枝  ← 最稳、收益最确定
  │    复用引擎已有的纯确定性函数：
  │      _match_memory_card_unit(unit, highlight)
  │      _match_memory_card_unit_with_position(unit, highlight, block_mask)
  │    对每个 (站位排列, 回忆集合)：
  │      逐卡逐 highlight 解析命中目标
  │      两级掩码都考虑：highlight.party_position 与 block.party_position
  │    掩码命中空槽 / 无角色满足其他选择器
  │      → 该卡在此站位下收益为 0 → 直接淘汰该组合（不跑战斗）
  │
  └─ 静态属性合成
       239/264（91%）的效果是 battle_start 纯静态属性修正
       在"影子战场"上按引擎同样的规则累加
       → 得到 5 个角色的最终属性向量
       ⚠️ 注：不能靠 battlefield() 直接读，回忆在战斗执行中才应用
          （见 3.1 的验证结果）；需复用 _apply_memory_card_structured_effect 的逻辑

第 2 层：筛选层（少量战斗）
  ├─ 用第 1 层算出的属性向量做代理排序（相关性待验证，见 3.2）
  ├─ 只对代理排序的前 N 名跑真实战斗
  └─ N 由预算决定，而不是由"阶段阈值"决定

第 3 层：决策层（预算驱动）
  ├─ 对候选逐个加种子，直到置信区间窄于"值得区分的最小差距"
  ├─ 分辨不了的候选**明确报告"无法区分"**，不按均值淘汰
  └─ 交付：冠军 + 置信区间 + 与次优是否可区分
```

### 2.3 为什么这个方向能解决作者的核心问题

| 作者的问题（实测） | 新思路如何解决 |
| --- | --- |
| 站位配对几乎不消噪（r=+0.283），4 种子 3% 阈值 41.9% 翻转 | **不靠共同种子去"测"站位**——站位好坏由解析层算出来，战斗只用来验证少数候选 |
| 裸装代理关掉了站位价值机制 | **解析层直接用真实回忆集合**，不再有空回忆阶段 |
| 5,760 场花在最不可靠的判定上 | 92% 的效果零成本算出来，省下的预算用于**真正需要采样的残留 8%** |
| 720 种排列里大量无效组合 | 掩码匹配性剪枝能在**跑战斗前**淘汰一大批（例如某卡要求后排但后排是空位） |
| 阈值固定、不随噪声调整 | 决策层按**实测噪声**动态决定种子数 |

## 3. 关键待验证问题

这个思路的前提必须在动手前确认。按重要性排序：

### 3.1 解析层能否复现引擎的静态属性计算？——**部分验证，且发现一个重要修正**

我做了零战斗验证（`_analysis/verify_analytic_layer.py`），结果**修正了我自己的表述**：

| 观察 | 结果 | 含义 |
| --- | --- | --- |
| `battlefield()` 构造后，**空回忆 vs 六张卡**的我方属性 | **完全相同** | ⚠️ **回忆效果不在战场构造时应用** |
| 交换槽 0/3 后我方属性变化 | **2/5 角色变化** | 属性差异来自**角色本身**（不同角色不同面板），不是回忆 |

**修正**：回忆效果是在**战斗执行中**应用的（`battle_flow_controller.py:3497 _apply_memory_card_effects`），不在构造阶段。所以"解析层读出最终属性"不能简单靠 `battlefield()`。

**但这一发现反而更有利**——因为应用逻辑是**独立、可复用的纯函数**：

```python
_resolve_memory_card_targets(highlight)                      # :3682
_resolve_memory_card_targets_with_position(highlight, mask)  # :3698
_match_memory_card_unit(unit, highlight)                     # :3768
_match_memory_card_unit_with_position(unit, highlight, mask) # :3729
_apply_memory_card_structured_effect(...)                    # :3889
```

**关键结论**：目标解析是 `(unit, highlight, 位置掩码) -> bool` 的**纯确定性函数**（`:3687-3694` 只遍历存活单位做匹配，无随机）。所以**"哪张卡给谁"完全可以在不跑战斗的情况下算出来**——我的核心论断成立，只是实现路径要改：

> **不要重新实现属性计算，而是直接复用引擎自己的 `_match_*` / `_resolve_*` 系列函数**，在一个"影子战场"上做静态解析。

### 3.1.1 新发现的第三层掩码：`block_party_position`

`:3698` 的 docstring 揭示：

> 使用 **block 级别的位置位掩码** 过滤目标……用于"**変動**"类技能对**不同位置施加不同效果**。

**这意味着掩码有两级**：
1. `highlight.party_position` —— 卡片级（哪张卡作用于哪些槽）
2. `block.party_position` —— **效果块级**（同一张卡的不同效果作用于不同槽）

**这一级比卡片级更精细，也更容易被"同排互换"破坏。** 你的更正不仅适用于卡片级，还适用于这一级——进一步确认压缩站位空间的思路不可行。

**这个发现也提升了新思路的价值**：两级掩码的组合空间很大，**靠战斗搜索极难命中**，但**靠解析可以精确枚举**。

### 3.2 属性向量 → 得分的代理有多准？

**这是决定新架构成败的关键实验，仍未做。**

需要采样若干 `(站位, 回忆)`，同时记录（解析出的属性向量，真实得分），看相关性。约 40–60 场。

- 相关性高（>0.8）→ 第 2 层可大幅缩减战斗量，新思路收益巨大
- 相关性低 → 解析层只能用于**剪枝**（淘汰掩码不匹配的组合），仍需较多真实评估

**在数据出来前不能承诺收益。**

### 3.3 那 8% 的动态效果有多重要？

`turn_start`（8）、`periodic_start/end`（10）、`turn_end`（1）、`after_ally_attacked`（1）、`on_any_kill`（1）。

**需要确认**：这些是否足以让"静态属性最优"的配置在实战中失效。若有某张关键卡是动态的，解析层需要为它保留特殊的处理（例如把它归入"必须真实评估"的少数卡）。

## 5. 建议的下一步

**先做两个验证，再决定是否投入重构：**

1. **✅ 解析可行性（0 战斗）——已完成，结论有修正**
   验证发现：回忆效果**不在战场构造时应用**（空回忆与六张卡的 `battlefield()` 属性完全相同），而在战斗执行中（`battle_flow_controller.py:3497`）。
   **但目标解析本身是纯确定性函数**（`_resolve_memory_card_targets` / `_match_memory_card_unit` 等，只做存活单位匹配，无随机）。
   **结论：解析层可行，但要复用引擎的 `_match_*` 函数在"影子战场"上做，而不是重新实现属性计算。**
   下一步可做：写一个不跑战斗的 `resolve_targets(state) -> {card: [targets]}`，与引擎在真实战斗中的实际目标逐一对账。

2. **⚠️ 代理相关性（约 40–60 场）——未做，是决定性的**
   采样 `(站位, 回忆)`，记录（解析属性向量，真实得分），算相关性。
   - 相关性高 → 第 2 层能大幅省战斗，新思路收益大
   - 相关性低 → 解析层只能用于剪枝（但剪枝本身收益已确定）

**在实验 2 出数据前，我不建议开始重构。** 目前能确定成立的只有"掩码剪枝"这一项收益。
