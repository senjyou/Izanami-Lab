# 自动优化器算法评估：优劣势与可优化方向

> 评估对象：`Izanami-Lab-MacOS-integration-full-enhancements-v1112` 的 `src/optimizer/`（4,022 行 / 22 文件）
> 评估方法：源码逐行审读 + **实测真实战斗分数噪声**（复现轮：7 组站位对 + 3 组回忆对 × 10 共同种子 = 200 场；每个配对自成一个案例、20 场，低于项目 100 场/案例上限）
> 结论前提：不保留 AI 学习；算法不照搬，按需重构。

---

## 0. 核心结论

**这份算法的工程实现质量高，但统计标定与实际噪声严重不匹配 —— 它花了大量战斗在区分它根本区分不了的东西。**

三个实测事实决定了全部结论：

| 实测项 | 数值 | 含义 |
| --- | --- | --- |
| 单场分数原始 CV | **5.22%**（7 组站位对的一致值） | 同一配置换种子，分数波动约 ±5% |
| 回忆替换的配对 SD | **0.52%**（corr **+0.997**） | 配对比较极有效，消除 **99%** 方差 |
| **站位替换的配对 SD** | **5.25%**（pooled corr **+0.283**，95% CI **[−0.067, +0.571]**） | **配对几乎不消噪，方差消除约 0%** |

> ⚠️ **本节数据已修订（重要）。** 初版报告用 2 组配对给出 corr = −0.104 / +0.126。本次用 **7 组站位对 + 3 组回忆对，各 10 个共同种子，共 200 场**重测，并加入**逐对自检**（断言"交换确实改变了配置"且"至少一个种子分数不同"）。
> 结论方向不变，但 **pooled 相关是 +0.283，不是负值**——初版的两个点估计样本太小（各 25 对），不可靠。下面用复现后的数字。

**核心结论（经复现验证）**：站位是这套算法的核心搜索维度（720 种排列），而**在这个维度上配对比较几乎不提供方差消除**：

| 维度 | 配对 SD | 相比原始 5.22% | 方差消除 |
| --- | ---: | ---: | ---: |
| 回忆 | **0.52%** | 降低 10 倍 | **99%** |
| 站位 | **5.25%** | 几乎不变 | **约 0%（−1%）** |

**但逐对差异极大——这才是关键**：7 组站位对的 corr 分别是 +0.592、+0.409、+0.236、+0.693、**−0.363**、**−0.324**、+0.494，**方差消除从 −24.5% 到 +60.4%**。

即：**换某些站位时配对有部分帮助，换另一些时完全帮倒忙。** pooled 值 (+0.283) 掩盖了这个双峰分布——**站位维度的配对效果不能用单个常数描述**，这直接支持"阈值应逐候选计算、而非用固定百分比"的结论。

按站位配对 SD（5.25%）换算，95% 置信带与算法阈值的关系：

| 种子数 | 95% 置信带 | 算法在此处的阈值 | 判定 |
| ---: | ---: | ---: | --- |
| 2 | **±7.43%** | — | 纯噪声 |
| 4 | **±5.25%** | 3%（4种子线） | 阈值只有噪声带的 **0.57 倍** → 无法判定 |
| 8 | **±3.72%** | 3% / 5% | 阈值只有噪声带的 **0.81 / 1.34 倍** → 边缘 |
| 16 | ±2.63% | — | 阈值开始有意义 |
| 50 | ±1.49% | — | 可靠 |
| 128 | ±0.93% | — | 可分辨 ~0.9% |

**要分辨 3% 的站位差距需要约 12 个配对种子；分辨 1% 需要约 106 个。** 而算法在 4 种子（噪声带 ±5.25%）上就用 3% 阈值淘汰——**这个阶段的淘汰基本由噪声决定，不是由实力决定。**

### 0.1 门槛稳定性实测（最直接的证据）

我直接用算法自己的规则（4 个共同种子、3% 线）枚举全部 4-种子子集，看判定是否稳定：

| 站位对 | 真实差距（10种子） | 4种子通过率 | 判定 |
| --- | ---: | ---: | --- |
| 中前 ↔ 中后 | **+3.47%** | **41.9%** | **不稳定** |
| 左前 ↔ 中前 | +7.40% | 1.4% | 稳定淘汰 |
| 其余 5 组 | −14% ~ −16.5% | 100% | 稳定通过 |

**关键一行是"中前 ↔ 中后"**：真实差距 3.47%（正好卡在 3% 线附近），4 种子通过率 **41.9%** —— 即**同一对配置，换一组 4 种子，约六成概率被淘汰、四成概率晋级**。这正是"阈值 ≈ 噪声带"时的典型行为。

**另一个重要发现**：8 组站位对中，`back-left <-> back-right`（两个后排位互换）**在 10 个种子上给出完全相同分数** —— 说明**部分站位排列在当前阵容下是完全等价的**。720 种排列中可能含大量冗余（见 2.11）。

## 1. 优势（值得保留的设计）

### 1.1 评价口径纯净，不重造物理

`engine.py:103-114` 只做一件事：调官方 `TacticalExerciseController.execute_battle()`，取 `result["score"]["total_score"]`。**没有自建伤害或评分公式**。这意味着优化目标和用户实际战斗完全一致，不会出现"优化器说好、实战不好"的口径漂移。

附带一个正确性细节：`engine.py:83` 强制 `memory_ids=sorted(...)`，配合 `BattleDataView` 的惰性深拷贝隔离技能状态——**保证同一配置在搜索各阶段得到完全相同的引擎输入**。

### 1.2 进程边界干净，可测试性好

- `src/optimizer/` **零 tkinter、零 gui 依赖**（22 文件逐个验证）。算法可独立跑、独立测。
- spawn + 每 worker 最多 1 个在途任务 + 顺序缓冲上限 `32×worker`，**结果按派发顺序入缓存**，慢任务不会打乱可复现性。
- 预算账本 `_budget_spent() = max(done, submitted_tasks)`——**失败/未知任务也占预算，不被当成"没花掉"**。这是很成熟的记账。

### 1.3 共同种子（paired）比较的方向是对的

作者选择了正确的比较方式：所有候选在同一组种子上评分，绝不拿不同种子的均值横向比。实测证明**在回忆维度上这个选择收益极大（消除 98% 方差）**。方向正确，只是没有针对站位维度做适配（见 2.1）。

### 1.4 诚实性极高

代码注释反复主动声明局限，不夸大：

| 原文 | 位置 |
| --- | --- |
| "declared search heuristics, not tests of true expected damage or global optimality" | `layered_search.py:3` |
| "explicitly NOT a confidence interval" | `pair_gate` docstring:32 |
| "Bare scores never enter the equipped champion race" | `layered_search.py:3` |
| "Review samples were used for selection: this is an estimator, not holdout proof" | `combined_score.py:1` |
| "Caps are search heuristics, never significance tests" | `quick_review.py:1` |

这种诚实是重构时的宝贵资产——**它把"哪些结论不能下"写在了代码里**。

### 1.5 若干细节设计正确

- **8 ULP 同分判定**（`bare_preselection.py:31`）：用 `max(1e-12, 8*max(ulp(a),ulp(b)))`，不用显示分数，不因四舍五入拆散并列组。
- **记忆无序集合语义**：共享回忆与槽位无关，用 `C(n, 6-r)` 而非排列，语义正确。
- **缓存键 = 规范化完整配置的 SHA256**（`model.py:362`），且**只含参战角色**——未上场候选的参数不影响键，避免缓存碎片。
- **停止语义保守**：未完成种子组不发布均分；已派发任务保守占预算；错误优先于停止。

## 2. 劣势（有实测或源码证据）

### 2.1 【最严重】站位筛选用"空回忆"当代理，而站位×回忆存在强耦合

**证据**（`bare_preselection.py:133`、`layered_search.py:194/217/295`）：

```python
run.state(row['positions'], [])     # 零张回忆卡！
```

裸装筛选阶段把 **720 个站位在完全不装回忆的情况下**各评 2→4→8 个种子，据此淘汰站位。但最终方案是"站位 + 6 张回忆"的联合配置。

**问题**：站位决定目标选择、行动顺序、前后排关系；回忆提供大量静态/触发效果。二者耦合很强——**某个站位在空回忆下很差，配上特定回忆可能反超**（作者在 `docs/OPTIMIZER_V29.md:76` 自己承认："可能遗漏在特定回忆搭配下优秀的站位"）。

更关键的是**实测数据显示这个代理特别不可靠**：两个独立的站位替换测试，配对相关性分别是 **−0.104** 和 **+0.126**（都≈0，95% CI 均含 0），配对消除的方差只有 10% 甚至为负。这意味着"站位 A 比 B 好"这件事**在不同种子下几乎无相关性**——用 2/4/8 个种子（置信带 ±5.9%/±4.2%/±3.0%）去判定这种量，**筛选结果近似随机**。

**代价**：默认无约束时 `720 × 8 = 5,760` 场（`docs/OPTIMIZER_V29.md:37`），是整条流水线最贵的阶段，却建立在最不可靠的判定上。

### 2.2 阶段阈值与噪声标定不匹配（可量化的错配）

| 阶段 | 种子 | 实测 95% 置信带（站位） | 使用阈值 | 结论 |
| --- | ---: | ---: | ---: | --- |
| 4 种子资格 | 4 | ±4.19% | 3% | 阈值 < 噪声 → 形同虚设 |
| 8 种子资格 | 8 | ±2.97% | 3% | 与噪声带相当 → 边缘 |
| 最终线 | 8 | ±2.97% | 5%（95%线） | 勉强超过噪声带 |
| 快速复评首轮 | 8 | ±2.97% | 5% | 同上 |
| 快速复评末轮 | 256 | ±0.52% | 0.5% | 阈值 ≈ 噪声带 |

**推论**：这些"筛选"在低种子阶段几乎不淘汰真正有实力的候选，只淘汰运气差的；高种子阶段阈值又恰好卡在噪声带上。**整个阶梯的淘汰压力分布是错位的**——真正的问题在于**它把宝贵的复评种子预算花在了本可以用更少种子做完、且判据本就不成立的阶段上**。

补充：`quick_review.empirical_gap` 已经用了正确做法（`mean > max(ratio×ref, 3×SE)`，即阈值与噪声取较大者），**但这个正确做法没有推广到裸装预选阶段**——那里仍是纯固定百分比（3%/5%）。

### 2.3 入围数量随联合空间线性增长，无上界（可导致预算爆炸）

`layered_review_percent = 10%`，`min(3, ceil(joint_total × 10%))`：

| joint_total | 入围候选 | 仅"首轮 8 种子"就要 |
| ---: | ---: | ---: |
| 70 | 7 | 56 场 |
| 525 | 53 | 424 场 |
| 2,520 | 252 | 2,016 场 |
| 50,400 | 5,040 | **40,320 场** |

**没有绝对上限**。`merged: quick_review` 的名额上限（64/32/16/8/4/4）只在**复评之后**才生效，无法阻止入围阶段本身的规模爆炸。在小预算下这会直接掏空预算（"预算不足完整首轮8种子复评"，`layered_search.py:423`）。

### 2.4 默认配置无法启动（可用性缺陷）

实测（`audit_defaults.py`）：

```
positions.total = 720, layered_base_seeds = 2
minimum = 1440
budget  = 200   ->  budget < minimum -> 拒绝启动
```

`SearchSettings()` 的默认 `budget=200` 与默认无约束站位空间（720）矛盾：**用户按默认值直接开始，会收到"预算不足以开始完整裸装预选：至少1440场"**。默认值组合不可用，用户被迫先理解站位空间与预算的关系。

### 2.5 两套筛选实现长期共存（维护负担）

`layered_search.preselect()` 有两条互斥分支：

- **快速分支**（`quick_preselection is not None`）→ 调 `bare_preselection.run`（V2.9）
- **严谨分支**（`:214-274`）→ 用 `elite_reference` / `paired_gate` / `elite_gate`（V2.8）

默认配置（layered + quick + filter）**只走快速分支**，严谨分支是 60 行在默认路径上永不执行的代码。两套实现语义相近但不同（例如同分判定：`bare_preselection.same_score` 有 `1e-12` 下限，`joint_admission.tied_score` **没有下限**），是**语义漂移的温床**。

### 2.6 大量死字段与一次性诊断

全仓库零消费者的输出字段（子代理逐字段核对）：

```
spread、early_gate、four_review_qualified、review_admitted、
position_filter_approximate、score_semantics、allowed_drop_percent、
initial_leader_threshold_count、initial_elite_threshold_count、
reference_four_scores、reference_eight_scores、four_reference_gap
```

其中 `layered_search.py:228-231` 的两个 `threshold_count` 更糟：**零消费者，但每行要跑 4 次 `paired_gate`**（O(P×E) 的纯浪费）。

`memory_exhaustive_limit=500` 在 layered 模式**完全不被使用**（只服务 legacy/memory 路径），却仍作为可调参数暴露。

### 2.7 单配置维度上的搜索是"伪搜索"

在 layered 默认参数下，`memory_ids` 常常全为"必选"（`MemorySpace.total = C(0,0) = 1`）。此时所谓"联合覆盖"退化成**只搜站位**，而站位筛选已经被 2.1 的代理问题污染。**算法在默认输入下实际只有一个有效维度**，但为它付出了两个维度的复杂度。

### 2.8 两处真实缺陷（已逐行核实）

**缺陷 A：严谨复评路径缺失 `try/finally`，被打断会泄漏 `evaluation_limit`。**

对比两条路径的写法：

| 路径 | 设置 | 恢复 | 保护 |
| --- | --- | --- | --- |
| 快速复评 | `quick_review.py:75` | `:126` | ✅ **有 `try:`(77) / `finally:`(125)** |
| 严谨复评 | `statistical_review.py:93` | `:146` | ❌ **整个文件没有任何 `try`/`except`/`finally`** |

严谨路径在 `:93` 设 `search.evaluation_limit = s.budget - reserve`，只在 `:146`（正常走完循环后）恢复为 `s.budget`。

**触发条件（已确认可达）**：循环体内的 `search.estimate(...)`（`statistical_review.py:113`）在预算不足时会 **raise `Stopped`**（`search.py:407-408`）：

```python
if self._budget_spent() + needed > self.evaluation_limit:
    raise Stopped("预算不足以完成当前种子集合")
```

`Stopped` 沿调用栈向上传播（经 `review_dispatch` → `layered_search.run` 的 `except Stopped`），**`:146` 永不执行**。

**实际影响有限，但确实存在**：`layered_search` 随后调用 `combine()` 与 `finish()`，两者都不再触发评估，所以最终结果正确；`evaluation_limit` 的泄漏只影响该实例后续的记账展示。**若将来重构成"复评后还需评估"的流程，这会变成一个静默的预算错误。** 快速路径已正确加了 `finally`，说明这是遗漏而非设计。

**缺陷 B：`layered_search` 对 `combine()` 的重复调用。**
`review_dispatch.py:19` 的 `finally: combine(search)` 已保证调用，`layered_search.py:434` 的 `except Stopped` 分支又调一次。当前**幂等**（`combined_champion` 被整体重算），但属于冗余调用；若 `combine` 将来带上副作用则会重复执行。

### 2.9 重构时必须知道的守卫（否则改一行就红）

这是一份**被测试强锁**的代码库，重构前必须知道锁在哪：

| 守卫 | 锁定方式 | 涉及文件 |
| --- | --- | --- |
| `tests/optimizer_source_guard.py` | `SCHEDULED_FILES` 内做 **AST 归一化对比**（允许评估循环适配） | `bare_preselection.py`、`quick_review.py`、`final_review.py`、`memory_search.py`、`position_search.py`、`search.py` |
| 同上 | **不在** `SCHEDULED_FILES` 内的做**逐字节对比**（`assertEqual(current, previous)`，`:79-80`） | `statistical_review.py`、`combined_score.py`、`review_dispatch.py`、`memory_validity.py`、`joint_admission.py`、`scheduling.py` |
| `tests/fixtures/integration_manifests.json` | **sha1 blob 校验** | 含 `quick_review`、`final_review`、`combined_score`、`review_dispatch`、`statistical_review`、`search` 等 |

**含义**：任何"保持算法不变"的重构，只要碰到 `statistical_review.py` / `combined_score.py` / `review_dispatch.py` 的**一个字节**，测试就会红。这与本报告的结论直接冲突——**P1（重新标定阈值）必然要改 `quick_review.py`（受 AST 守卫）与 `bare_preselection.py`（受 AST 守卫）**，`quick_review.GAPS` 正是被 `test_optimizer_v32.py:234` 用一个"把 `.05` 改成 `.06`"的负向用例显式锁定的。

**结论**：算法改动与"通过现有测试"不可兼得。必须**先决定放弃/重写这批守卫**，而不是试图在不触发它们的前提下改算法。

### 2.10 三处 GUI 相关的数据结构不对称（重写时易踩）

| 项 | 快速复评 | 严谨复评 | 决赛 |
| --- | --- | --- | --- |
| `rounds[]` 是否有 `completed` | 有（`True`） | **没有该字段** | 有 |
| `comparisons` 类型 | **dict** | dict | **list** |

GUI 的 viewmodel 已按这种不对称**写死**了渲染分支。新 GUI 若统一处理这三种结构，需要显式做适配层。

另有一处流程差异：**快速复评走 `evaluate_cohorts` 分批调度，严谨复评走逐键 `estimate` 串行**。这正是 V3.2 文档所述"严谨统计复评走原串行路径"。**重写时不要顺手统一**——统一会改变预算记账与并行行为。

### 2.11 【实测新发现】720 种站位排列中含有大量等价冗余

复现测试中，`back-left <-> back-right`（3 号位与 5 号位互换，两个后排位）**在 10 个不同种子上给出完全相同的分数**。

**含义**：在当前阵容与 Boss 下，这两个站位是**完全等价**的（不只是"接近"，是逐场次相同）。而 `PositionSpace` 用 `itertools.permutations` 枚举全部 **6! = 720** 种排列，**不做任何等价性去重**。

**代价推算**：若等价类普遍存在（后排内部互换在多数阵容下可能都等价，因为目标选择通常只区分前/后排而非具体左右位），则 720 种里有相当比例是重复计算。按裸装预选 `720 × 8 = 5,760` 场计，**可能有一半以上是白跑的**。

**这也解释了 2.2 的核心矛盾**：算法花 5,760 场去分辨 720 种站位，其中一部分根本无从分辨（等价），另一部分则被噪声淹没——**真正需要分辨的那部分，预算反而不够**。

**建议**（P0 的一部分）：在枚举前做**等价类合并**。可行性可先用少量战斗验证——例如测若干组"同排互换"与"跨排互换"，若同排互换普遍零差异，就可在 `PositionSpace` 里按"排内无序"压缩空间。注意这需要引擎语义保证（若某些技能依赖具体左右位，则不能压缩），**必须实测确认而非假设**。

> 本报告的作者在开发复现脚本时曾出现一处缺陷（交换后未写回状态），导致首轮复现得出"站位完全无影响、r=+1.000"的**虚假结果**。修正后加入了逐对自检（断言交换确实生效、且至少一个种子分数不同），上表数据均通过自检。**记录于此以说明数据可信度边界。**

## 3. 可优化方向（按收益/成本排序）

### P0：重构站位评估，砍掉裸装代理（预计节省 50–80% 战斗）

**问题**：5,760 场（最贵）用于最不可靠的判定，且空间本身可能含大量等价冗余。

**方案 A——先压缩空间，再放弃裸装预选**：
1. 先实测确认等价类（见 2.11）——若"排内互换"普遍零差异，`PositionSpace` 按排内无序压缩，720 可能降到几十~一百量级。**这一步单独就能省下大部分预算。**
2. 压缩后直接做联合搜索（站位 × 回忆一起采样，局部爬山），每个候选评的就是**最终目标函数**，不再用空回忆当代理。

**方案 B——保留分层但改判据**：若无法安全压缩空间，则：
- 用 **1 个种子**做全站位粗筛（只砍掉明显极差尾部），
- 再用剩余预算在**入围的少数站位 × 回忆**上做联合评估。

**必做的实测前置**：本次复现已确认（7 组站位对，自检通过）：
- 站位配对几乎不消噪（pooled r=+0.283，方差消除约 0%），而回忆配对消除 99%；
- 逐对差异极大（方差消除 −24.5% ~ +60.4%），**不能用单个常数描述站位维度**；
- 至少一组站位对完全等价（10/10 种子同分）。

**建议下一步**：再测 **6–8 组"同排内互换"**（后排 3 个位置两两、前排 3 个位置两两）。若普遍零差异，方案 A 的第 1 步收益巨大且实现简单；若差异显著，则走方案 B。

### P1：按实测噪声重新标定阈值与种子阶梯

以实测噪声为基准（而非拍脑袋的 3%/5%）：

```
要分辨的差距 δ，所需配对数 n ≈ (1.96 × SD_paired / δ)²
```

用实测值代入得到**维度相关的种子需求**：

| 维度 | 配对 SD | 8 种子可达 | 分辨 3% 需要 | 分辨 1% 需要 |
| --- | ---: | ---: | ---: | ---: |
| 回忆 | 0.52% | ±0.37% | ~1 | ~2 |
| 站位 | 5.25% | ±3.72% | **~12** | **~106** |

**维度间的种子需求差 100 倍以上。** 建议：

- **按维度差异化**：回忆维度 8 种子已远超需要（±0.37%）；站位维度需要 ~12 种子才够 3%、~106 才够 1%。
- **阈值改为噪声的倍数**：`max(用户阈值, 2×SE)`，而不是固定百分比。`quick_review.empirical_gap` 已经这么做了（`mean > max(ratio*ref, 3*se)`）——**把这个正确做法推广到裸装预选阶段即可**。
- **明确区分"分辨不了"与"更差"**：当 `δ < 2SE` 时报告"无法区分，保留"，而不是按均值删掉。**实测证据**：真实差距 3.47% 的站位对，4 种子判定在 41.9% 的情况下翻转。
- **阈值逐候选计算**：站位维度的配对效果逐对差异极大（−24.5% ~ +60.4%），用全局常数必然次优。

### P2：给入围数量加绝对上界

`min(3, ceil(joint_total × 10%))` 改为同时受绝对上限约束，例如 `min(200, ...)`，或按剩余预算反推：`admission = min(joint_total, remaining_budget // (first_round_seeds × ...))`。**避免 50,400 联合空间下 40,320 场的首轮**。

### P3：修掉默认值组合

- 把默认 `budget` 提高到能覆盖默认站位空间（≥1440），或
- 把默认 `layered_filter` 设为 `False`（不预筛，直接联合覆盖），或
- 在默认无约束时**自动提示**并提供"仅约束站位/缩小空间"的引导。

### P4：删除重复实现与死字段

- 删除严谨分支或快速分支之一（推荐保留快速，删除 `layered_search.py:214-274` 的 V2.8 路径），统一同分判定语义（8 ULP 是否带 `1e-12` 下限必须二选一）。
- 删除 2.6 列出的零消费者字段，其中 `layered_search.py:228-231` 优先（省 CPU）。
- `memory_exhaustive_limit` 若不再有 legacy 路径，从 UI 移除。
- 修 2.8 的两处缺陷：给严谨路径补 `try/finally` 恢复 `evaluation_limit`；去掉 `layered_search:434` 的重复 `combine()`。

### P-1【前置】先决定如何处理测试守卫

**这是所有 P0–P5 的前置条件，不是可选项。** 见 2.9：

- `statistical_review.py` / `combined_score.py` / `review_dispatch.py` / `memory_validity.py` / `joint_admission.py` / `scheduling.py` 被**逐字节锁定**。
- `quick_review.py` / `final_review.py` / `bare_preselection.py` / `memory_search.py` / `position_search.py` / `search.py` 被 **AST 锁定**，且 `quick_review.GAPS` 有显式的"改成 .06 必须失败"负向用例。
- 另有 `integration_manifests.json` 的 sha1 blob 校验。

**P1 必然要改 `quick_review.py` 与 `bare_preselection.py`** —— 这两处都在守卫范围内。因此正确顺序是：

1. 先决定守卫的去留：**要么整体移除这批"算法冻结"测试**（它们的存在意义是保护作者已验证的行为，而你正要改变该行为），**要么把守卫重写为只保护你打算保留的不变量**。
2. 再动算法。否则会陷入"改算法 → 测试红 → 被迫回退"的循环。

**建议**：保留 33 个**行为级**测试（`test_optimizer_*.py` 里断言真实计算结果的），**删除/重写 AST 与字节级守卫**。行为测试验证"算法对不对"，守卫只验证"算法没变"——后者在主动重构时是纯粹的阻力。

### P5：把"诊断"与"算法输出"分层

当前 `report_fields()` 在一个函数里混合了算法数据和约 55 个展示字段。建议：

- 算法只返回 `entries` / `admitted` / `bare` / `joint` 等**真实数据**；
- 单独一个序列化模块负责构造 GUI/JSON 视图；
- 这样 GUI 重写与算法演进可以独立进行，也便于把 JSON 体积降下来（`parallel_diagnostics` + `memory_evaluations` + `elite_summary` 是体积主因）。

## 4. 建议的新算法骨架（若"不完全照搬"）

```
1. 空间定义
   - 站位：PositionSpace（保留，720/硬约束逻辑正确）
   - 回忆：MemorySpace（保留，无序集合语义正确）

2. 采样（替换裸装 2→4→8）
   - 分层随机采样 N 个 (站位, 回忆) 联合配置
   - N 由预算反推，而非按站位数的固定倍数

3. 评估（替换逐种子阶梯）
   - 每个候选先评 1–2 种子做粗排
   - 对粗排前 K 名追加种子，直到 2SE < 目标分辨力
   - 明确"分辨不了就保留"，不做噪声驱动的淘汰

4. 收敛
   - 局部搜索（换 1 个站位 / 换 1 张回忆 / 同时换）
   - 每步用配对比较，且**只在达到足够种子数后才淘汰**

5. 交付
   - 冠军 + 置信区间（不是单点均分）
   - 明确标注"与次优无法区分"的情况
```

**核心变化**：从"多阶段阈值筛除"改为"**预算驱动的逐步加种子 + 只在统计可分辨时才淘汰**"。这样每一次淘汰都有依据，预算花在真正需要分辨力的候选上。

## 5. 需要你决策的问题

1. **是否继续测"同排内互换"的等价性？**（推荐，见 2.11 / P0）已发现一组完全等价（10/10 种子同分）。再测 6–8 组可判断 720 种里有多大比例是冗余——**这是收益最大且最容易落地的一步**（若成立，`PositionSpace` 加一层排内去重即可，不动算法结构）。
2. **测试守卫怎么处理？**（见 P-1）这是改算法的前置条件。是整体移除、还是重写为保护新不变量？
3. **保留哪些维度？** 若"换人/词条"要开放，搜索空间再乘数级，P2 的上界问题会更严重。
4. **目标使用者画像是？** 若多数用户只想"给我一个比现在好的方案"，那 P0 的简化（少阶段、少战斗）比"证明最优"更有价值。
5. **预算上限预期？** 决定 P1 的种子阶梯设计（例如是否保留 256 种子）。
6. **是否保留严谨复评（Student-t + Bonferroni）？** 它的统计处理是整份代码里最严谨的部分，但依赖"配对差值独立近似正态"假设——实测显示**站位维度配对几乎不消噪**（r=+0.283），该假设在该维度上缺乏支持。它也是唯一缺 `try/finally` 的路径。

## 6. 一句话总结

**工程实现扎实（进程边界、预算记账、缓存键、诚实性都很好），但统计标定与实际噪声脱节：它在 4 个种子上用 3% 固定阈值淘汰站位，而实测站位维度的 95% 噪声带是 ±5.25%（阈值反而比噪声窄）；同时它的核心搜索维度（站位）上配对比较几乎不消噪（r=+0.283），而回忆维度是 +0.997。**

**最省战斗的改法不是调阈值，而是两步：① 先实测并合并站位等价类（已发现至少一组完全等价的站位，720 种里可能大量冗余）；② 砍掉"空回忆裸装预筛"这个既贵又不可靠的代理阶段，改为直接在联合空间上做预算驱动的逐步加种子，且只在统计可分辨时才淘汰。**
